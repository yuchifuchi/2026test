# 業務システム調達シリーズ 全10本 執筆パック

**読者は「1〜2年前の自分」。** 初めて業務システムの調達を任され、何から手をつけるか分からない情シス・総務・経営企画の担当者。

肩書きで書かない。専門家として語らない。**実践記録として書く。**この立て付けなら年次は弱点になりません。

各記事の【実体験】は、あなたにしか書けない部分です。ここが空欄のまま公開すると、AIが書いた記事と区別がつかなくなります。**最低1本につき2箇所は、自分の案件の具体で埋めてください。**

# 1. 初めて業務システムの調達を任されたとき、最初にやるべき3つのこと

**読者の状態**:「調達やっといて」と言われた。とりあえずベンダーに問い合わせようとしている。

**フック**
> 最初にやるべきことは、ベンダーを探すことではありません。むしろ、それが一番やってはいけないことです。最初の3つは全部、社内で完結します。

### 構成

**① 決裁のルートと金額の閾値を確認する**
- 最終決裁者は誰か。いくらから稟議か、いくらから役員会か
- 相見積もりは何社必要か(社内規程にあることが多い)
- 予算はどの費目から出るか。今期か来期か
- ここを知らずに進めると、最後に「その金額なら役員会」と言われて数か月戻ります

**② 現行の契約と費用を洗い出す**
- 今、何にいくら払っているか
- **保守契約の更新月と、解約通知の期限**
- 通知期限(3か月前など)から逆算すると、スケジュールが一気に厳しくなることがあります。これに最初に気づくかどうかで、案件の余裕がまるで変わる

**③ 「この案件が失敗するとしたら、原因は何か」を先に書き出す**
- 現場が使わない / 予算が足りない / 移行が終わらない / 決裁が下りない
- これがそのまま、後の評価軸の重み付けになります

**締め**
> 3つとも社内の話です。ベンダーに会うのはこの後。順番を逆にすると、あとで必ず戻ります。

【実体験】決裁ルートを確認せずに進めて手戻りした話 / 解約通知期限に気づいた時期と、そこから逆算して何を諦めたか

# 2. 要件をまとめる前にベンダーへ声をかけると、なぜ比較できなくなるのか

**読者の状態**:情報収集のつもりでベンダーに問い合わせようとしている。悪いことだと思っていない。

**フック**
> 「まず話を聞いてみよう」は、比較検討を自分から壊す行為です。理由は、ベンダーが悪いからではありません。

### 構成

**なぜ壊れるのか(ロジックを丁寧に)**
1. 要件がない状態で声をかけると、ベンダーは**自社製品が得意な土俵**で提案を組み立てる
2. A社は機能で、B社は価格で、C社は運用体制で勝負してくる → **評価軸が揃わない**
3. 軸が揃わない提案は比較できない。人は比較できないとき「印象」で決める → **提案書が上手い会社が勝つ**
4. さらに悪いのは、**自分の要件が提案に汚染される**こと。最初に見た製品の機能一覧が、そのまま「要件」になってしまう

**「でも要件が分からないから聞きたい」への回答**
- その気持ちは正しい。ただし**情報収集と提案依頼を分ける**
- 情報収集フェーズでは「提案はまだ受け取りません」と明言する。もらうのはカタログ、一般的な機能範囲、価格レンジまで
- **本命に最初に声をかけない。**要件が固まっていない状態での接触は、本命ほど後にする

**要件は完璧でなくていい**
- 「必須 / あれば望ましい / 対象外」の3分類だけで足りる
- この3分類があるだけで、提案の土俵が揃います

【実体験】最初に声をかけた会社の資料が、そのまま要件定義の下敷きになってしまった話

# 3. 相見積もりが比較不能になる理由と、条件を揃えるための質問リスト 【有料】

**読者の状態**:3社から見積もりが来た。金額も項目もバラバラで、並べても比べられない。

**フック**
> 3社の見積もりが並んだのに、どれが安いのか分からない。これは自分の読解力の問題ではありません。比較できない見積もりが届いているだけです。

### 無料部分:比較不能になる4つの原因

1. **前提条件が違う** — 利用者数、拠点数、データ量、稼働時間。同じ数字を全社に渡していない
2. **含む範囲が違う** — A社は移行費込み、B社は別途、C社は「別途お見積り」
3. **期間が違う** — 初年度だけ / 5年 / 保守は別紙
4. **粒度が違う** — 「一式」と明細が混在している

**揃えるためにやること**
- 見積依頼書に前提条件を全部書く(利用者数、同時アクセス、拠点、データ件数、稼働時間、想定稼働開始日、連携の有無、移行対象)
- **費目の枠を先に指定する**:ライセンス / 構築 / カスタマイズ / データ移行 / 教育 / 初年度保守 / 次年度以降年額
- 5年総額を必ず出させる
- 「一式」は必ず分解を求める

### 有料部分:条件を揃えるための質問10問

1. 見積の内訳を、ライセンス/構築/カスタマイズ/移行/教育に分けてください
2. 5年間の総額と、年度ごとの内訳をください
3. **この見積に含まれない作業を、明示的に列挙してください** ← 最も効く一問
4. 当社側に発生する作業と工数(人日)を、工程別にお示しください
5. 利用者が◯名増えた場合、費用はどう変わりますか
6. 法改正対応の費用は保守料に含まれますか、別途見積ですか
7. バージョンアップの費用は誰が負担しますか。カスタマイズ部分の改修は
8. 最低利用期間と、途中解約時の取り扱いを教えてください
9. 値上げが発生する場合の通知時期と条件を教えてください
10. 見積の有効期限と、期限後の価格の考え方を教えてください

**3番が効く理由を必ず解説すること。**「含まれるものは何ですか」と聞くと全社が「全部含みます」と答えます。「含まれないものを列挙してください」と聞くと、初めて差が出ます。

【実体験】「一式」の分解を依頼して金額が変わった話 / 3社の見積もり金額の分散がどれくらいあったか

# 4. 業務システムの見積もりに出てこない「後から来る費用」 【1本目に公開】

**読者の状態**:見積もり金額を予算だと思っている。

**フック**
> ベンダーの見積もりが1,000万円だったとして、実際に必要なお金は1,000万円ではありません。差分のほとんどは、見積書に項目として存在しません。

### 構成:出てこない費用 10種

1. **自社側の人件費** ← 最大。要件確認、テスト、マスタ整備、現場調整、研修受講。40人日なら実質どれくらい乗るかを計算して見せる
2. **マスタ整備** — 移行前にデータを綺麗にする作業。重複、表記ゆれ、廃番。想定の3倍かかる
3. **並行稼働期間の二重コスト** — 旧システムの保守料を切れない期間
4. **周辺機器の更新** — 端末、OS、ブラウザ、プリンタ、ハンディ、回線
5. **帳票の作り直し** — 「できます」でも有償なことが多い
6. **追加ライセンス** — 想定外の利用者(パート、派遣、閲覧のみの人)
7. **教育の2周目** — 異動と新入社員。初回研修が無償でも2回目は有償
8. **法改正対応** — 都度有償の契約だと毎年出ていく
9. **バージョンアップ時の検証工数とカスタマイズ改修費**
10. **解約時のデータ移行費** — 出るときにも金がかかる

**締め**
> これらを見積もり時点でゼロと置くと、必ず予算が足りなくなります。特に1番(自社工数)をTCOに入れるだけで、社内の判断が変わることがあります。

【実体験】実際に想定外だった費用を1つ。金額を出せないなら「見積の何%相当」で書く

**この記事はシリーズの看板です。**具体性が命なので、ここには最低3つ自分の実例を入れてください。

# 5. パッケージ・SaaS・スクラッチ、どこで切り分けるか

**読者の状態**:「うちの業務は特殊だからスクラッチしかない」と言われている。あるいは自分でそう思っている。

**フック**
> 規模で決めるものだと思われていますが、違います。判断軸は「その業務が、自社の稼ぎ方に直結しているかどうか」です。

### 構成

**軸①:その業務は競争優位か**
- 競争優位でない業務(経理、勤怠、経費)→ SaaS。業務をシステムに合わせる
- 競争優位に直結する業務 → カスタマイズまたはスクラッチを検討する価値がある
- 中間 → パッケージ + 最小カスタマイズ

**軸②:変化の速度**
- 法改正・制度変更が頻繁 → SaaS(ベンダーが対応してくれる)
- 自社都合で頻繁に変えたい → 自社でコントロールできる形

**比較表**

| | パッケージ | SaaS | スクラッチ |
|---|---|---|---|
| 初期費用 | 中〜高 | 低 | 高 |
| 5年TCO | 中 | 中〜高 | 高 |
| 業務適合 | 中 | 低〜中 | 高 |
| 法改正対応 | ベンダー(有償のことも) | ベンダー(通常含む) | 自社 or 都度有償 |
| 変更の自由度 | 低 | 最低 | 最高 |
| 属人化リスク | 低 | 最低 | 高 |
| 5年後の身動き | 中 | 高(乗り換えやすい) | 低 |

**最も言いたいこと**
> スクラッチは「今」最適で、「5年後」に最悪になりやすい。作った時点では業務に完璧に合っているのに、作った人がいなくなり、変更のたびに費用がかかり、他システムと繋がらない。

**判断の一言**
> 「この業務は、5年後も同じやり方をしているか?」Yes なら適合重視、No なら変更容易性重視。

【実体験】「特殊だ」と言われた業務が、実は標準機能で足りた話(または本当に特殊だった話)

# 6. 現場ヒアリングで「今のやり方のままで」と言われたときの進め方

**読者の状態**:現場が非協力的だと感じている。説得しようとして疲れている。

**フック**
> 現場は保守的なのではありません。**変更のコストを自分が払うから**抵抗しているだけです。これは完全に合理的な反応です。だから、説得ではなくコストの配分を変えます。

### 構成

**① 「今のやり方」を要件として受け取らない**
- 「なぜそうしているか」を3回聞く。だいたい「昔からそう」「Aさんがそう言った」に行き着きます

**② 業務を3つに分類する**
- (a) 法令・取引先都合で変えられない
- (b) 自社ルールだが、理由がある
- (c) 理由がすでに失われている
- **(c) が想像より多い。**ここを可視化するだけで議論が進みます

**③ 変更の理由を「システムの都合」にしない**
- 「システムがそうだから」は最も反発を招く言い方
- 「この変更で月◯時間減ります」に翻訳する

**④ 決定権を最初に明確にする**
- ヒアリングの冒頭で「これは決定の場ではなく、情報収集の場です」と言う
- 誰が決めるかを曖昧にすると、永久に決まりません

**⑤ 例外の頻度を実測させる**
- 「たまにこういうケースがある」の"たまに"を数える
- 年2回のためにカスタマイズを入れると、非常に高くつきます

**言ってはいけない一言**
> 「それは運用でカバーしましょう」──誰がカバーするかを決めずにこれを言うと、稼働後に必ず火を噴きます。

【実体験】理由が失われていた業務の実例 / 例外の頻度を数えたら実際は何件だったか

# 7. 稟議を通すために、経営層向け資料へ何を書くか 【有料】

**読者の状態**:機能比較表を作って稟議に出そうとしている。

**フック**
> 経営層が知りたいのは3つだけです。**いくらか / なぜ今か / 失敗したらどうなるか。**機能の話は、一行も要りません。

### 無料部分:経営層が見ている3点と、やりがちな失敗

**やりがちな失敗**
- 機能一覧を貼る(読まれない)
- 「他社より優れている」とだけ書く(根拠がない)
- リスクを書かない(隠していると受け取られる)
- 効果を「業務効率化」とだけ書く(測れない = 評価できない)

### 有料部分:資料の構成8ブロック

1. **現状の課題を、金額と時間で書く** — 「非効率」ではなく「月◯時間、年◯万円相当」
2. **なぜ今か** — 保守期限、法改正、人員減、EOL。今やらないと何が起きるか
3. **5年総額と年度別の支出** — 予算計画に乗る形で
4. **比較検討の経緯** — 何社を、どの軸で比べたか。**ここが弱いと「他社は見たのか」で差し戻される**
5. **選定理由** — 3行で。長いと読まれない
6. **他社を選ばなかった理由** — これがないと「なぜこれ?」に答えられない
7. **想定リスクと対応** — 評価で低い点をつけた項目が、そのまま材料になる
8. **効果の測定方法** — いつ、何をもって成功と判断するか

→ 4・5・6・7 は、評価シート(03_稟議用サマリ)から自動で文面が出ます。ここでシートに接続。

【実体験】差し戻された経験と、そのとき何が足りなかったか。**これが書ければ記事の説得力が跳ね上がります**

# 8. デモで見るべき点と、デモでは絶対に分からない点

**読者の状態**:デモを見て「良さそうだった」と思っている。

**フック**
> デモは「できること」を見せる場です。**「できないこと」は構造上、絶対に出てきません。**この非対称性を前提に組み立てないと、デモは時間の無駄になります。

### 構成

**デモで見るべき点**
- **自社の実データを使わせてもらう。**サンプルデータのデモは意味が薄い
- **一番使う画面の操作回数を数える。**1日100回使う画面で2クリック多いと、年間で膨大な差になります
- **例外処理を出させる。**返品、訂正、取消、締め後の修正。正常系はどの製品もきれいです
- **エラーメッセージを見る。**現場が読んで意味が分かるか
- **情シスではなく利用部門に触らせる。**「見る」と「触る」は別物
- その場で「今の作業を、この画面でやってみてください」と言う

**デモでは絶対に分からない点**
- データ量が増えたときの速度(デモは100件、本番は50万件)
- 同時アクセス時の挙動
- 月次・年次処理の重さ(デモでは絶対にやりません)
- 障害時の挙動と復旧手順
- サポートの実際の質(**営業の対応と保守の対応は別部隊です**)
- バージョンアップで壊れるかどうか
- 3年後、担当者が変わったときの引継ぎ

**埋め方**
> 参考顧客に聞く。質問は一つで足ります。「導入して、一番困ったことは何でしたか」

【実体験】デモで見抜けた点 / デモでは見抜けず稼働後に判明した点。**後者があると記事の価値が跳ね上がります**

# 9. 契約前に確認しないと後で詰む項目 【有料・シートの配布記事】

**読者の状態**:選定が終わって安心している。契約書は法務に回せば済むと思っている。

**フック**
> 選定が終わった時点で、案件の8割が終わったと感じます。ですが、後から詰むポイントはほぼ全部、契約書の中にあります。

### 無料部分:なぜ契約前が最後の分岐点か
- 契約後は交渉力がゼロになる。**要求を通せる最後のタイミングが契約前**
- 法務は法的リスクを見ますが、**運用上のリスクは情シスしか見られない**

### 有料部分:チェックリスト14項目

1. **保守の範囲** — 操作質問/設定変更/マスタ追加/障害調査/データ復旧。どこから有償か、文書で
2. **SLA** — 一次回答時間、復旧目標、稼働率、未達時の扱い
3. **最低利用期間と中途解約** — 違約金、通知期限
4. **解約時のデータ** — 機械可読形式で全件出せるか、費用、**契約書に条項があるか**
5. **値上げ条件** — 通知時期と上限
6. **法改正対応の費用負担**
7. **バージョンアップ** — 強制か任意か。カスタマイズ部分の改修費は誰が持つか
8. **再委託** — 実際に作業するのは誰か。再委託先の管理責任
9. **知的財産権** — スクラッチの場合、成果物の権利とソースコードの扱い
10. **エスクロー** — ベンダー倒産時にソースが手に入るか(重要システムの場合)
11. **データの保管場所** — 国内か国外か。委託先の監査
12. **検収条件** — 何をもって完了とするか。検収後の瑕疵対応期間
13. **納期遅延時の扱い**
14. **契約の自動更新** — 更新を拒否する場合の通知期限

# 10. 選定に落ちたベンダーの提案から学べること

**読者の状態**:選定が終わり、落選提案を捨てようとしている。

**フック**
> 落選した提案書は、実は選定プロセスで最も情報量が多い資料です。捨てる前に、5つだけ拾ってください。

### 構成

1. **自分の要件の穴が見える** — 落ちた会社だけが指摘してきた項目。それは自分が見落としていた要件かもしれない
2. **相場が分かる** — 3社の見積もりの分散そのものが情報。極端に安い/高い理由を聞く
3. **次回の交渉材料になる** — 他社が標準で持っていた機能は、本命にも要求できる
4. **不採用通知の出し方で、次の関係が決まる** — 数年後にまた声をかけることがあります
5. **落選理由を伝えると、情報が返ってくる** — 「その要件なら、こういう手もありました」

**不採用通知に書くこと / 書かないこと**
- 書く:選定軸、どの軸で差がついたか、感謝
- 書かない:他社の金額、他社名、社内の事情

**最大の学び**
> 落選提案は3年保管する。次の調達のとき、最初の情報収集がまるごと省けます。

【実体験】落選提案から拾えた具体的な情報 / 不採用通知への返信で得たもの
